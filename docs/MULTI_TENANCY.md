# NEWAY TMS — Multi-Tenancy

Tenant isolation is non-negotiable. Company A must never see, infer, or modify Company B's data, through any path: API, WebSocket, files, search, jobs, notifications, AI, exports, or error messages.

Related: [ARCHITECTURE.md](../ARCHITECTURE.md) · [DATABASE.md](DATABASE.md) · [RBAC.md](RBAC.md)

---

## 1. Model

```
Platform (one deployment)
└── Companies (tenants)            companies.id = company_id
    ├── Departments
    ├── Memberships (user ↔ company)  a user can belong to several companies; each membership has its own roles
    │   └── Employees / Drivers      people records inside the company
    └── Company resources            fleet, loads, money, documents, settings, …
```

Two administrative levels:

| Level | Who | Sees |
|---|---|---|
| Platform | `platform_users` with a platform role (super_admin, support, billing, read_only) | Companies, plans, subscriptions, platform users, platform settings, system health, integrations catalog, platform audit, cross-company analytics (aggregates only) |
| Company | Members with company roles (owner, admin, …) | Only their active company's data |

A platform user has **no membership** and no company context by default. To look inside a company (support), they open an explicit **support session** with a reason; it is time-limited, recorded in `support_sessions` and `platform_audit_logs`, and shown as a banner to the platform user. Company owners can see in their audit log that a support session occurred.

## 2. Isolation strategy: shared database, shared schema, defense in depth

One PostgreSQL database and one schema. Every company-scoped table carries `company_id`. Isolation is enforced by **three independent walls**; any single failure is caught by the others.

| Wall | Mechanism | Catches |
|---|---|---|
| 1. Request context | The active `company_id` is derived **only** from the authenticated session's membership and stored in an `AsyncLocalStorage` context. Client-supplied company ids in body, query, or headers are ignored (and logged as a security event if present) | Spoofing |
| 2. Data access layer | All repository access goes through a tenant-scoped `db` handle that injects `company_id` on inserts and adds `WHERE company_id = ctx.companyId` to reads/updates/deletes. Unscoped access requires an explicit, reviewed `withPlatformScope()` call that is only allowed inside `platform` and `iam` modules | Forgotten filters |
| 3. Row-level security | Every company table has `ENABLE ROW LEVEL SECURITY` with a policy `USING (company_id = current_setting('app.company_id', true)::uuid)` (and matching `WITH CHECK`). Each transaction begins with `SET LOCAL app.company_id = '<id>'`. The application connects as a role **without** `BYPASSRLS`. If the setting is missing, the policy evaluates to no rows | Bugs in wall 2, raw SQL, ad-hoc scripts |

Fail-closed rule: if the context has no company id when a company-scoped repository is used, the call throws before touching the database.

### Why shared schema and not schema-per-tenant or database-per-tenant

- Operational simplicity: one migration path, one backup, one connection pool; hundreds of tenants stay cheap.
- Cross-tenant platform analytics and plan limit enforcement are simple aggregates.
- RLS gives database-enforced isolation comparable to separate schemas for the threat model here (application bugs), with far less machinery.
- Schema-per-tenant remains available for a customer that contracts for it (§8).

## 3. Tenant resolution

1. `AuthGuard` validates the access token and loads the session.
2. `TenantGuard` reads `session.membership_id`, loads the membership, verifies `status = active` and the company `status ∈ {trial, active}`, and sets `ctx = { companyId, membershipId, userId, roles, permissions, timezone }`.
3. Routes under `/api/v1/platform/**` require a platform principal and set no company context. Support sessions set `ctx.companyId` from the `support_sessions` row and mark the context `viaSupport = true` (audit rows and logs carry it).
4. WebSocket connections are authenticated the same way; the socket is joined to the room `company:<id>` and can never subscribe to another room.
5. Background jobs and event handlers receive `companyId` explicitly as part of the job payload/event row and open their own tenant context; a handler cannot iterate companies without `withPlatformScope()`.

Switching company: `POST /api/v1/auth/switch-company {membershipId}`; the server checks the membership belongs to the session's user, rotates the session, and returns a new token. The UI company switcher lists only the user's memberships.

## 4. Database implementation

```sql
-- once per company table (generated by migrations)
ALTER TABLE loads ENABLE ROW LEVEL SECURITY;
ALTER TABLE loads FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON loads
  USING (company_id = current_setting('app.company_id', true)::uuid)
  WITH CHECK (company_id = current_setting('app.company_id', true)::uuid);

-- per transaction (done by the db handle)
BEGIN;
SET LOCAL app.company_id = '018f...';
-- queries
COMMIT;
```

- Two database roles: `neway_app` (no BYPASSRLS; used by API and worker) and `neway_admin` (migrations, maintenance).
- Composite unique constraints always include `company_id` (`uq (company_id, unit_number)`), so uniqueness is per tenant.
- Foreign keys between company tables are plain FKs; RLS on both sides prevents cross-tenant references from being readable, and a `CHECK` trigger on insert asserts the referenced row's `company_id` matches for the handful of high-risk links (load → driver/truck/trailer/customer/broker, invoice → load, settlement → driver, document → owner). This closes the "reference an id you guessed" hole.
- Platform tables (`companies`, `plans`, `subscriptions`, `platform_users`, `platform_settings`, `platform_audit_logs`, `support_sessions`) have no RLS and are only touched inside `withPlatformScope()`.

## 5. Isolation beyond the database

| Surface | Rule |
|---|---|
| Object storage | Keys are `{companyId}/…`; signed URLs are minted only for keys under the context's company prefix |
| Search | `search_index` rows carry `company_id` and RLS; queries are always scoped |
| Cache | Cache keys are prefixed with `company:<id>:`; no cross-tenant cache reads |
| Notifications & WebSocket | Recipients are resolved inside the tenant context; rooms are per company |
| Exports & reports | Generated inside a tenant context; files stored under the company prefix |
| Jobs | Every job payload includes `companyId`; the worker opens the context before running the handler |
| AI | Query tools run under the asking user's tenant and permissions; prompts never include another company's data; usage caps are per company |
| Integrations | `integration_accounts` are per company; webhook routes include the account id and verify it belongs to the provider signature |
| Logs & errors | Problem responses never include other tenants' identifiers; 404 (not 403) for a resource that exists in another tenant, so existence is not leaked |
| Sequences | `load_number` etc. are per company; identical numbers in two companies are expected |
| Rate limits & quotas | Per company (and per user) so one tenant cannot starve another |

## 6. Per-tenant configuration

`settings` (key/value jsonb) holds company preferences with typed accessors in code: timezone, week start, fiscal settings, load status labels (`status_definitions`), maintenance defaults, notification defaults, AI policies, feature flags within plan limits. `plans.limits` caps users, trucks, storage, and AI tokens; the `platform` module enforces limits at creation points and the UI shows usage.

## 7. Testing

Isolation tests run on every endpoint and every event handler (Phase 3 onward, extended as modules appear):

1. Create Company A and Company B with one user each and one of every entity.
2. As A's user, request every B resource by id → expect 404; list endpoints → B rows absent; search → B absent; WebSocket → no B events; signed URL for a B document → 403.
3. As A's user, attempt writes referencing B ids (assign B's driver to A's load) → 404/422.
4. As A's user, send `companyId = B` in body/query/header → ignored, logged.
5. Direct SQL test: with `SET app.company_id = A`, `SELECT * FROM loads` returns only A; with no setting, returns nothing; `INSERT` with `company_id = B` fails the policy.
6. Platform user without a support session hitting a company route → 403; with a support session → allowed and audited.
7. Job handler invoked with company A payload cannot read B (context is set by the runner, not the handler).

A schema lint test asserts every company table has `company_id NOT NULL`, RLS enabled and forced, and a policy named `tenant_isolation`.

## 8. Future: dedicated isolation for a tenant

If a customer requires physical separation, the same code can run against a dedicated database for that company: the tenant resolver maps `companyId → connection`. Because all data access is through the tenant-scoped handle, no module code changes. This is deliberately not built in v1.
